# Elfrey Scene Browser — план работ

> Браузер всех сцен из библиотек (compendium-паков) установленных модулей — включённых и выключенных, — а также паков системы, паков мира и сцен самого мира. Foundry VTT v13 (основная цель) и v14. Всё делается из UI модуля внутри мира: никаких внешних скриптов и сервисов. Документ рабочий: фазы отмечаем по мере выполнения.

## 0. Цель и рамки

**Цель.** Мастер открывает одно окно и видит **все сцены**: дерево «источник → модуль → папки паков → пак → папки внутри пака», сетку карточек с превью, поиск по дереву и по сценам, фильтры. Для включённых модулей данные берутся живьём из `game.packs`; для выключенных модуль сам читает LevelDB паков прямо из браузера (файлы отдаются сервером как статика), складывает результат в кэш в `Data/` и потом работает с кэшем. Сцену из выключенного модуля можно импортировать в мир **не включая модуль** — у нас есть её полный JSON, а картинки выключенных модулей сервер отдаёт как обычно.

**Входит:**
- индексатор внутри модуля: обход `game.modules` (все установленные, с флагом `active`), паков системы и мира, `game.scenes`; чтение LevelDB выключенных модулей по HTTP в Web Worker; кэш `Data/elfrey-scene-browser/index.json`, инкрементальное обновление, прогресс и отмена — всё кнопками в окне;
- браузер: дерево, сетка, поиск, фильтры, сортировка, панель деталей, действия (открыть, импортировать, показать в компендиуме, перетащить в сайдбар, копировать UUID);
- две локали (ru/en), одна кодовая база на v13 и v14, без сборки.

**Не входит (пока):** избранное/теги, правка сцен, экспорт списков. Кандидаты в последнюю фазу.

**Сцены из приключений (Adventure-паки).** Многие модули поставляют сцены не отдельным Scene-паком, а внутри документа Adventure (массив `scenes` целиком, со встроенными стенами/токенами). Таких паков 111 на v13 и 8 на v14. Модуль их читает и показывает как узел «модуль → приключение → папки → сцены»; импорт идёт из встроенного JSON (штатный `importFromCompendium` для Adventure-пака одну сцену не отдаёт).

## 2. Архитектура

```
 источники                                   модель                      UI
 ───────────────────────────────────────     ──────────────────────      ───────────────────
 game.scenes + game.folders (мир)        ─┐
 game.packs (вкл. модули, система, мир)  ─┤   Source → Module/Pack
    └ getIndex({fields}) + pack.folders   ├─▶ → PackFolder → Pack   ─▶  дерево | сетка | детали
 index.json (кэш из Data)                ─┤   → Folder → Scene          поиск, фильтры, действия
    ▲                                     │
    │ FilePicker.upload (GM)              │
 индексатор (Web Worker):                ─┘
    fetch CURRENT?v → MANIFEST?v → *.ldb?v / *.log?v
    → разбор LevelDB (snappy, таблицы, журнал) → !scenes! / !folders! + счётчики по ключам
```

### 2.1 Откуда берётся каждая сцена
| Источник | Имена / превью / папки | Размеры, сетка, счётчики стен и т.п. |
| --- | --- | --- |
| сцены мира | `game.scenes` живьём | живьём (документы уже в памяти) |
| пак включённого пакета | живой индекс `getIndex({fields})` | лёгкие поля из индекса; счётчики — из кэша, если пак проиндексирован |
| пак выключенного модуля, есть в кэше | кэш | кэш |
| пак выключенного модуля, в кэше нет | заголовок модуля и паки из манифеста, статус «не проиндексирован» | — |

Счётчики живьём не запрашиваем: `getIndex({fields:["walls"]})` заставит сервер сериализовать все стены пака (у 100-мегабайтных паков это минуты и сотни мегабайт). Индексатор считает их по ключам LevelDB без разбора значений — поэтому и включённые паки выгодно прогнать через индексатор один раз.

### 2.2 Индексатор (кнопка «Индексировать» в окне)
1. Собрать список паков типа Scene: `game.modules` (все, включая выключенные), `game.system.packs`, `game.world.packs`. Для каждого — путь папки (`pack.path`), статус пакета.
2. Подпись пака: `CURRENT?v` → имя манифеста; `HEAD` на манифест и на каждый `.ldb`/`.log` из манифеста → `Content-Length`. Подпись = набор имён + размеров + версия пакета. Совпала с кэшем → пропуск.
3. Файлы читаются последовательно по одному, разбираются в Web Worker (`scripts/leveldb/worker.js`), результат — папки, сцены (лёгкие поля), счётчики. Память ограничена самым большим файлом (таблицы ~2 МБ, журналы — до десятков МБ).
4. Прогресс: паки / байты / текущий пак; кнопка «Отмена» — уже разобранные паки сохраняются. Ошибка разбора одного пака не останавливает остальные (статус `error` с текстом).
5. Каждый прочитанный пак сразу пишется отдельным файлом `Data/elfrey-scene-browser/packs/<collection>.<timestamp>.json` через `FilePicker.upload` (папки создаются при первом запуске). Перед стартом показываем план: сколько паков читать из файлов и сколько мегабайт, сколько через API, сколько не изменилось, — и переключатель «индексировать и подключённые паки».
6. Подключённые паки, чьи файлы читать нельзя (v14) или не нужно (переключатель выключен), пишутся в кэш через `getIndex({fields})` + `pack.folders` (стратегия `api`): без счётчиков, зато после выключения модуля сцены останутся в списке.

Первый прогон на v13 при запущенном мире: 26 паков выключенных модулей, 187 МБ; с включёнными — 477 МБ. С localhost — секунды-минуты; повторные прогоны — только изменившиеся паки.

### 2.3 Ридер LevelDB в браузере (`scripts/leveldb/`)
| Файл | Что делает |
| --- | --- |
| `varint.js`, `crc32c.js` | varint32/64, маскированный CRC32C (проверка записей журнала и блоков; при несовпадении — предупреждение, не остановка) |
| `snappy.js` | распаковка snappy (литералы и три вида копий), ~80 строк |
| `log-reader.js` | формат журнала: блоки 32 КБ, записи FULL/FIRST/MIDDLE/LAST, сборка фрагментов. Используется и для `.log`, и для `MANIFEST` |
| `write-batch.js` | разбор WriteBatch из журнала: `seq`, `count`, записи Put/Delete |
| `manifest.js` | VersionEdit (теги comparator/logNumber/nextFile/lastSeq/compactPointer/deletedFile/newFile/prevLog) → живой набор таблиц и номер текущего журнала |
| `table-reader.js` | SSTable: футер (48 байт, magic), индексный блок → блоки данных, трейлер блока (тип сжатия + CRC), префиксное сжатие ключей и рестарт-точки, внутренний ключ = ключ + 8 байт (`seq << 8 | type`) |
| `pack-reader.js` | объединение таблиц и журнала «новее побеждает» с учётом удалений; из `!scenes!`/`!folders!` — JSON, из вложенных ключей — счётчики по `sceneId`; нормализация старых полей (`img` → `background.src`, старая сетка) |
| `worker.js` | обёртка: принимает файлы, отдаёт прогресс и результат |

Самопроверка на этапе разработки: тот же ESM-код запускается в Node и сравнивается с `classic-level` на всех паках папки данных (число сцен, id, папки, счётчики, при `--embed` — собранные встроенные документы). Это инструмент разработчика, в поставку и в UI он не входит: `node dev/check-reader.mjs --data …/data-v13 --copy-locked` (см. `dev/README.md`).

### 2.4 v14
Файлы БД недоступны, поэтому на v14 в первой версии: включённые пакеты — живьём, сцены мира — живьём, выключенные модули — из кэша, если он есть, иначе статус «не проиндексирован» с честным объяснением. Запасной путь для v14 (**отдельное решение, фаза 6**): «временное включение» — модуль включает выключенные модули без кода (`core.moduleConfiguration`), после перезагрузки индексирует их через `game.packs` (сервер подключает паки через `updateActivePacks`), восстанавливает конфигурацию и перезагружает ещё раз. Две перезагрузки мира и чужие модули во включённом состоянии на минуту — поэтому только по явному запросу.

### 2.5 Отвергнутые варианты
Внешний Node-сканер и watcher под launchd — противоречат требованию «всё из UI модуля». Индекс в world-настройке — раздувает `settings` мира и привязывает кэш к миру, а не к папке данных. Постоянное включение модулей ради индексации — перезагрузки мира и риск для мира.

### 2.6 Кэш
Папка `Data/elfrey-scene-browser/` (настраивается), внутри `packs/<collection>.<timestamp>.json` — **по файлу на пак**. Сервер не позволяет перезаписывать не-медиа файлы и не даёт удалять, поэтому файл пака пишется заново только когда пак изменился (подпись: имя MANIFEST + имена и размеры таблиц и журналов + версия пакета), при чтении берётся самый свежий по метке времени, а вытесненные файлы модуль перечисляет с предложением удалить вручную. Кэш — **на папку данных**: наборы модулей v13 и v14 разные, папка модуля общая; `data-v13-test` индексируется отдельно (те же файлы, свой кэш). Формат файла пака:
```jsonc
{
  "schema": 1, "collection": "ag-dnd2024.dmg-scenes",
  "package": { "type": "module", "id": "ag-dnd2024", "title": "…", "version": "1.2.3" },
  "label": "DMG Scenes", "path": "modules/ag-dnd2024/packs/dmg-scenes",
  "strategy": "files",                                 // files | api
  "status": "ok",                                      // ok | error
  "error": null, "scannedAt": "…", "coreVersion": "13.351",
  "signature": { "manifest": "MANIFEST-000272", "files": { "MANIFEST-000272": 167, "000005.ldb": 581324, "000274.log": 0 } },
  "warnings": [],
  "folders": [ { "_id": "6fqUFq5PtD28l5aN", "name": "Encounter Maps", "folder": null, "sort": 400000, "color": null } ],
  "scenes": [ {
        "_id": "dmgBarrowCrypt00", "name": "Barrow Crypt", "navName": "",
        "thumb": "modules/ag-dnd2024/assets/dmg/scenes/thumbs/dmgBarrowCrypt00-thumb.webp",
        "bg": "modules/ag-dnd2024/assets/dmg/scenes/barrow-crypt.webp",
        "w": 5160, "h": 6600, "grid": { "type": 1, "size": 120, "distance": 5, "units": "ft" },
        "folder": "6fqUFq5PtD28l5aN", "sort": 100000,
        "counts": { "tokens": 0, "walls": 452, "lights": 0, "notes": 0, "tiles": 0, "sounds": 0, "drawings": 0, "regions": 0, "templates": 0 },

Полные JSON сцен в кэше не храним — для импорта сцены из выключенного модуля пак перечитывается точечно (один пак, секунды), это редкая операция.

Только GM. Чистый ESM, без сборки — как pocket-app.

### 3.2 Модель и дерево
```
Мир
├─ Сцены мира (папки мира)
└─ Компендиумы мира → пак → папки → сцены
Система (dnd5e) → паки → …
Модули
├─ ag-dnd2024 ●  → packFolders → пак → папки компендиума → сцены
├─ baileywiki-content ○ (кэш от 13.09) → …
└─ some-module ◌ не проиндексирован → паки из манифеста (пустые)
● включён  ○ выключен, есть в кэше  ◌ выключен, кэша нет  ⚠ кэш устарел (подпись/версия изменились)
```
Папки паков — из `packFolders` манифеста (глубина ≤ 3), папки внутри пака — компендиумные (глубина ≤ 3). Висячие `folder` → корень пака (если есть `flags.cf.path` — попробовать восстановить, низкий приоритет). У каждого узла — счётчик сцен с учётом фильтра. Каждая сцена знает `source` (`world | live | cache`), `uuid` (если есть) и предвычисленную строку поиска.

### 3.3 Окно

- **Поиск.** Одно поле; токены через пробел — по И; регистр/диакритика/ё игнорируются; по имени, navName, пути папок, паку, пакету. Дерево раскрывает и подсвечивает ветки с совпадениями (по имени узла или по сценам внутри), остальные прячет. Задержка 150 мс.
- **Фильтры.** Источник/статус (мир, включённые, выключенные, без кэша); тип сетки; размер по большей стороне в клетках (≤ 20 / 21–40 / 41–80 / > 80); содержимое (стены / токены / свет / заметки / Levels); система; автор пакета. Сортировка: имя, пакет, размер, дата, число стен.
- **Сетка.** Карточки с `loading="lazy"`; без `thumb` — заглушка (фон в карточку не грузим); порции по 100–200 через IntersectionObserver; размер карточек — настройка.

## 4a. Исправления после первой обкатки пользователем (2026-09-14)

- **Поиск «переставал работать» в новой сессии.** Причина: сохранялся активный scope (выбранный в дереве узел) между сессиями; при следующем открытии он молча ограничивал выдачу, и поиск по остальным сценам давал 0. Механизм самого scope корректен (проверено: ограничение по czepeku даёт 8018 сцен). Решение: **scope, поисковый запрос и выбранная сцена больше не запоминаются между сессиями** (остаются preferences: раскрытые ветки, фильтры, сортировка); активный scope теперь показан удаляемым «чипом» рядом со счётчиком, чтобы он никогда не был невидимым. Проверено в браузере: свежее открытие → поиск работает, scope сброшен; чип появляется при выборе узла и очищается одним кликом.
- **Два крестика очистки поля.** Убран собственный крестик; поле `type="search"` само показывает штатный крестик, когда в нём есть текст.

## 4b. Доработки по запросу пользователя (2026-09-14)

## 4c. Сцены из приключений (2026-09-14)

Adventure-паки (тип `Adventure`) держат сцены встроенными в документ приключения. Реализовано:
- **Ридер.** Ключи `!adventures!` разбираются, из документа берутся полные сцены (`scenes`) и папки типа Scene (`folders`), помечаются служебным `__adv` (id+имя приключения). Счётчики — из встроенных массивов (как у сцен мира), а не из ключей `!scenes.*!`.
- **Источники.** В список включены паки `type: Adventure` с пометкой `kind`.
- **Индексатор.** Adventure-паки читаются только стратегией «файлы» (у API-индекса приключения нет встроенных сцен); на v14 без файлового доступа — только из кэша.
- **Дерево.** Пак → узел приключения (по одному на документ Adventure) → папки внутри приключения → сцены. У узла приключения иконка. В деталях — строка «Приключение».
- **Импорт.** Встроенные сцены не имеют собственного UUID (перетаскивание и «показать в компендиуме» недоступны), импорт — из полного JSON через `Scene.create`; папки при импорте: «модуль › приключение › внутренняя папка».
- **Оговорка.** У части приключений `thumb` указывает на папку мира автора и не грузится; фон при этом обычно есть и показывается в деталях.

Проверка `dev/check-reader.mjs` (расширен на Adventure-паки): **v14 — 18 паков, 965 сцен, 0 расхождений** (включая 8 Adventure-паков). Многосоставный пак ag-dragon-delves (10 приключений, 50 сцен) читается верно. В браузере на `data-v13-esb`: индексация 9 паков, 92 сцены из приключений, 11 узлов приключений в дереве, поиск и импорт сцены из приключения в папки «модуль › приключение › внутренняя» — работают.

## 4g. Офлайн-сборка кэша для v14 (2026-09-14)

`tools/build-cache.mjs` — отдельный Node-скрипт, собирающий кэш модуля вне Foundry: `node tools/build-cache.mjs --data <папка-данных>`. Нужен на v14, где сервер не отдаёт файлы библиотек клиенту (на v13 тоже работает). Использует только чистый ридер `scripts/leveldb` — без `classic-level`, без нативных модулей, без `npm install`; базы не блокирует, поэтому работает при запущенном мире. Пишет тот же формат кэша (те же `summarizeScene`/`summarizeFolder`, `schema: 1`, версионированные файлы `<pack>.<ts>.json`), удаляет устаревшие файлы, инкрементален по подписи. Проверено: на `data-v13-esb` собрал 11 паков / 8160 сцен, повторный прогон — всё «unchanged», и `SceneCache.load()` в браузере прочитал результат (11 паков, 8160 сцен, 0 ошибок, приключения на месте). Добавлен в release-zip и описан в README и `tools/README.md`.

## 4h. Импорт из выключенных модулей на v14 (2026-09-14)

Проблема: импорт сцены выключенного модуля дочитывал пак по HTTP (`?v=`), а на v14 сервер файлы библиотек не отдаёт → импорт падал. В кэше лежали только сводки, без полных документов.

Решение (вариант 1): `tools/build-cache.mjs --full-scenes` дополнительно пишет полный документ каждой сцены в `Data/<out>/scenes/<pack>/<sceneId>.json` (для Scene-паков встроенные документы прикрепляются через `embed`, у сцен приключений они уже инлайн; `__adv` вычищается). Импорт (`readDormantScene` в `actions.js`) сначала пробует этот файл (обычный JSON — работает и на v14), и только если его нет, падает назад на чтение пака по HTTP (v13). Флаг опционален: полные сцены ≈ объём самих паков (в тесте 314 МБ на 8160 сцен), на старте не грузятся, тянется один файл в момент импорта.

Проверено: сборка с `--full-scenes` (11 паков, 8160 сцен, пик ~2 ГБ RAM из-за czepeku), готовый файл отдаётся сервером (200, стены на месте), импорт через модуль создаёт сцену со стенами из готового документа. Картинки выключенных модулей сервер отдаёт и на v14, так что фон импортированной сцены грузится.

## 4i. Предупреждение о кэше на v14 (2026-09-14)

При загрузке мира на Foundry v14 (major ≥ 14) GM видит уведомление, если есть выключенные модули со сценами, которых **нет в кэше** (новый модуль) или чья **версия в кэше не совпадает** с текущей (модуль обновился). На v13 подавляется — там кэш можно собрать из UI. Логика в `main.js` (`warnIfCacheStale`, вызов из `ready` только для GM): `SceneCache.load()` + `listScenePackSources().filter(!live)`, сравнение по наличию записи и `package.version`; постоянное `ui.notifications.warn` с числом затронутых пакетов и подсказкой запустить `build-cache.mjs`. Проверено: при полном кэше — молчит; удаление файла кэша → пак попадает в «нет в кэше»; на v13 подавлено; текст локализуется (ru/en).

## 4j. Импорт и предупреждение на v14 — доработка по обратной связи (2026-09-14)

Пользователь на v14 не увидел сообщения и не смог импортировать. Причины и правки:
- **Импорт падал**, потому что кэш собран без `--full-scenes` (папки `scenes/` нет) → импорт дочитывал пак по HTTP → 403. Теперь `readDormantScene` на v14 (major ≥ 14), не найдя готового документа, сразу выдаёт понятную ошибку `ESB.Errors.NeedFullScenes` («пересоберите кэш с --full-scenes»), без глухого 403.
- **Сообщения не было**, потому что предупреждение срабатывало только на устаревший/неполный кэш сводок, а они были полные. Теперь `warnIfCacheStale` на v14 дополнительно проверяет наличие папки полных сцен (`FilePicker.browse` по `<cache>/scenes`) и показывает `ESB.CacheWarning.NoFullScenes`, если её нет.
- Мелочь: `build-cache.mjs` определял версию ядра по соседней папке `fvtt*` и для v14-данных показывал 13 — теперь берёт максимальный `coreVersion` среди миров папки данных.

Проверено на реальном v14 (отдельный инстанс `data-v14-esb`, fvtt14 + Node 24, порт 30214, мир `temple`): без `--full-scenes` — показывается предупреждение и импорт даёт понятную ошибку; после сборки с `--full-scenes` — предупреждение исчезает, импорт создаёт сцену (стены 440, фон из модуля).

**Превью (не баг модуля).** У ~51% сцен в кэше v14 миниатюра ведёт в папку мира автора (Scene Packer) или карта собрана из тайлов, а фон в сцене не задан — этих изображений нет на сервере ни на v14, ни на v13. Карточка уже подставляет фон, когда он есть; для таких сцен показать нечего. Возможное улучшение (не сделано): брать превью из самого большого существующего тайла — помогло бы части тайловых карт.

## 4k. Подтягивание актёров при импорте (2026-09-14)

Запрос: при импорте сцены из приключения/библиотеки подтягивать актёров, на которых ссылаются токены сцены. Проверено по данным: у сцен приключений токены ссылаются по `actorId`, и эти актёры лежат в самом документе Adventure (`actors[]`).

Реализация (для сцен из приключений, self-contained):
- Ридер: опция `includeActors` возвращает актёров приключения (`result.actors`).
- Воркер: опция `includeActors` возвращает актёров, на которых ссылаются токены целевой сцены (v13-путь).
- `build-cache.mjs --full-scenes`: рядом со сценой пишет `<sceneId>.actors.json` — полные документы нужных актёров (v14-путь).
- Импорт (`actions.js`): `readDormantScene` возвращает `{scene, actors}`; перед созданием сцены создаются актёры через `Actor.createDocuments(..., {keepId:true})` (id сохраняются → токены резолвятся; уже существующие актёры не трогаются) в папке актёров с именем корневой папки импорта.

Проверено на реальном v14 (`data-v14-esb`, приключение dmdave): импорт сцены «The Grotto» (8 токенов) создал 4 актёра (25→29), все 8 токенов резолвятся в мировых актёров, создана папка актёров.

Отдельный Actor-компендиум (2026-09-14): `build-cache.mjs --full-scenes` теперь резолвит актёров токенов и из **отдельных Actor-паков** того же модуля — `readActorDocs` читает актёра вместе с встроенными предметами/эффектами (ключи `!actors.items!…`, как стены у сцен). Проверено на v14: beard-share (отдельный bb-actors) — импорт сцены создал 3 актёров с предметами, все 7 токенов резолвятся; hotdq-sceny/beard-share совпадают по id на 96–100%, ravenloft — 0% (Scene Packer переписал id токенов, связь потеряна) → актёры не находятся, импорт сцены работает как обычно.

Ограничения: v13-путь через воркер тянет актёров только из приключений (для отдельных Actor-паков на v13 — нет; но v14/prebuilt покрывает); live-импорт активных Scene-паков (`importFromCompendium`) актёров не тянет; если id токенов переписаны (Scene Packer), связь восстановить нельзя.

## 4m. Заметность сообщения о кэше на v14 (2026-09-14)

Пользователь не увидел уведомления, потому что оно (всплывашка из `warnIfCacheStale` на `ready`) показывается только когда кэш неполон/устарел или нет полных сцен — а он уже собрал кэш с `--full-scenes`. Всплывашку легко пропустить среди прочих при загрузке, поэтому добавлен **постоянный баннер в самом окне браузера** (`_prepareContext` → `#v14CacheState`): на v14 при наличии выключенных паков показывает «нужно (пере)собрать кэш» (если пакет не в кэше/устарел) и «нет полных сцен — импорт недоступен, соберите с --full-scenes» (если папки `scenes/` нет). Проверено на v14: с полными сценами баннера нет, после удаления папки — баннер появляется. (Поймана и исправлена до коммита опечатка: в `browser.js` не был импортирован `listScenePackSources`.)

## 4n. Окно вместо всплывашки о кэше (2026-09-14)

По просьбе пользователя загрузочное уведомление о кэше заменено на **окно `DialogV2` с галочкой «Больше не показывать»** (`warnIfCacheStale` в `main.js`). Галочка ставит клиентскую настройку `hideCacheWarning` (config:true — её можно вернуть в настройках модуля), тогда окно больше не появляется. Постоянный баннер в окне браузера сцен галочкой не подавляется — остаётся как ненавязчивый индикатор. Проверено на v14: без полных сцен окно появляется (заголовок, текст, чекбокс); галочка + «Понятно» → `hideCacheWarning=true`, окно закрывается; после перезагрузки окно не появляется.

## 4o. Внутримодульная сборка кэша для v14 (2026-09-15)

Запасной путь для тех, кто не может запустить `tools/build-cache.mjs`. Кнопка «Из модулей» (в футере окна, только v14) открывает список установленных модулей со сценами. Ключевое: на v14 включённый пакет читается через сокет-API `pack.getDocuments()` — это даёт **полные** документы (сцены со стенами/токенами, приключения со встроенными сценами и актёрами), поэтому получается полноценный кэш с импортом, хотя файлы по HTTP по-прежнему 403.

Реализация:
- `scripts/apiindex.js` — `apiIndexPacks(collections, cache)`: `getDocuments()` → сводки + полные сцены + актёры (из приключения или из Actor-паков модуля через `getDocuments`), запись через `cache.write` (сводка) и `cache.uploadInto` (полные сцены/актёры в версионированную папку `scenes/<coll>/<ts>/`). Запись именно в версионированную папку — потому что сервер не даёт перезаписывать файлы; путь пишется в запись кэша как `scenesPath`, а `model.js`/`actions.js` его учитывают.
- `scripts/buildcache.js` — диалог выбора; включённые модули индексируются сразу; выключенные проходят через машину состояний: сохраняем конфигурацию, включаем выбранные + наш модуль, ставим `pendingBuild` (клиентская настройка), перезагрузка; в `ready` (`resumePendingBuild`) индексируем, возвращаем конфигурацию, чистим задание, перезагрузка. При ошибке конфигурация всё равно восстанавливается (finally).

Проверено на реальном v14 (`data-v14-esb`): включённый beard-share проиндексирован через API (17 сцен, полные документы), после выключения сцена импортируется с актёрами (7/7 токенов резолвятся); оркестрация для dmdave (включить→индекс→вернуть→перезагрузка) отработала — задание очищено, dmdave выключен, кэш содержит его сцены; кнопка и диалог со списком модулей отображаются.

Ограничения: только v14 (на v13 работает штатная индексация из UI); две перезагрузки мира; включение модулей запускает их код (нужен пустой мир); запись больших паков идёт по одному файлу через `FilePicker.upload` — для гигантов медленно.

Доработки по обратной связи (2026-09-15): в диалоге добавлены «Выбрать все / Снять все»; при индексации (и немедленной, и после перезагрузки) показывается модальное окно ожидания с прогрессом (`openWaitDialog`), при resume оно висит до следующей перезагрузки; после немедленной индексации окно браузера перечитывает кэш (`refreshBrowser`, `app.cache=null`), иначе включённые модули «не давали видимого эффекта» (их сцены и так видны живьём, но кэш теперь пишется и виден статус). Проверено на v14.
